## A library, not a server

SQLite is a C library that implements an SQL database engine. Your program links the library, calls its functions, and the library reads and writes a file on disk. No server process runs. No port listens. Nothing starts at boot, and nobody has to create a database user before you can store a row.

Almost everything else in this book follows from that one design decision.

When you query a client/server engine like Postgres or MySQL, your application opens a network connection to a separate program, sends the SQL text over a wire protocol, and waits. The server parses the statement, plans it, runs it, and streams rows back over the same connection. Two processes are involved, often two machines.

When you query SQLite, the SQL never leaves your process. The library parses the statement, compiles it to bytecode, runs the bytecode, and pulls the pages it needs out of the database file through ordinary file reads. A query that returns a single row by primary key takes microseconds, because nothing crosses a network and nothing crosses a process boundary. There is no connection to establish, no handshake to authenticate, and no serialization step to pay for on the way out.

This also means SQLite has no opinion about who you are. It does not know about users, roles, or grants. Access control is whatever the operating system says about the file. If your process can open the file, it can read and write every table in it.

The library is small enough to be beside the point in most builds. Compiled with default options and optimized for size, the whole engine lands between about 590 KB and 750 KB depending on the platform, with no dependencies beyond the C standard library and a handful of operating system calls for file access. That is why it ends up inside phones, browsers, and firmware where a database server would never fit.

## The single-file model

A SQLite database is one file. The schema, every table, every index, every view, every trigger, and all the data live inside it. Copy the file and you have copied the database. Delete the file and the database is gone. Send the file to a colleague and they open it with the same library and see exactly what you see, on a different operating system and a different processor.

Two temporary companion files can sit next to the main one while the database is in use. In the default rollback journal mode you may see a `-journal` file. In write-ahead logging mode you will see `-wal` and `-shm` files. Both are working files rather than parts of the database, and both are cleaned up when the last connection closes. <ChapterRef id="transactions-and-concurrency" /> explains what they contain and <ChapterRef id="durability-crashes-and-recovery" /> explains what to do when you find one left behind after a crash.

The format itself is stable to an unusual degree. Every release of SQLite 3 can read and write files created by SQLite 3.0.0, which shipped on 2004-06-18, and the developers commit to keeping that true for all future SQLite 3 releases. Older releases can usually read files written by newer ones as well, though that direction is not guaranteed once a new feature writes something the old code has never seen. The US Library of Congress lists SQLite as a recommended storage format for long-term preservation of digital content, which shows how stable it is considered to be.

## Where it runs, and why it is everywhere

The SQLite developers claim it is likely used more than all other database engines combined, and estimate more than a trillion databases in active use. That estimate comes from counting smartphones, each of which holds hundreds of SQLite files.

SQLite ships inside every Android, iOS, macOS, and Windows install. Firefox, Chrome, and Safari all use it. So do Dropbox, Skype, iTunes, and QuickBooks. PHP and Python bundle it in their standard distributions. Most televisions, set-top boxes, and car infotainment systems have a copy. The developers put it in the top five most deployed software modules of any kind, probably behind zlib.

Four things explain the reach.

The code is public domain. There is no license to read, no attribution clause, and no lawyer to consult before shipping it in a commercial product.

There is nothing to install. The source is distributed as a single large C file, the amalgamation, which you drop into your build.

SQLite is very well tested. As of version 3.42.0 the engine was roughly 156,000 lines of C, against about 92 million lines of test code and test scripts, a ratio near 590 to 1. The core has 100% branch coverage and 100% MC/DC coverage, the standard used for avionics software.

The file format does not move. Firmware written in 2009 can still open a database written by a phone shipped last week.

### The amalgamation

The second of those four deserves more than a sentence, because it is the mechanism behind most of the reach.

SQLite is not developed as a single file. The core is 111 separate C files as of version 3.37.0, with another 22 implementing extensions that most builds want. What ships instead is the amalgamation, a generated file called `sqlite3.c` that concatenates all of them into one translation unit, accompanied by a single header, `sqlite3.h`, whose contents also appear in the first few thousand lines of the C file. As of the end of 2021 the amalgamation held about 238,000 lines, or 145,000 once blank lines and comments are removed.

The practical effect is that adding a database engine to a program looks like adding a source file. There is no build system to adopt, no package to resolve, no shared library to locate at runtime, and no version to install on the target machine. You put two files in your source tree and hand them to the compiler you already use.

That is the whole integration story on a system with a C compiler, and it is why SQLite turns up in set-top boxes and washing machines where nobody was going to provision a database server.

One consequence matters for application work and is easy to miss. Because the engine is compiled from source into whatever links it, the SQLite version your program runs is the version of the amalgamation your driver vendored when it was built. It is not a system package you can upgrade independently, and two libraries in the same process can each carry their own. <ChapterRef id="ecosystem-map" /> covers how to find out what you actually have.

### Open source, not open contribution

SQLite is open source but not open contribution. Anyone can read the source and anyone can use it for anything, but the small core team does not merge outside patches. That is a deliberate choice to maintain control over reliability. Turso maintains libSQL, a fork of SQLite that does accept contributions, and is separately building Turso Database, a from-scratch rewrite of the engine in Rust. <ChapterRef id="turso-and-libsql" /> covers both, along with Turso Cloud, and untangles which name refers to which thing.

## What SQLite is good at

Embedded devices and internet-of-things hardware. Phones, televisions, game consoles, cameras, watches, appliances, cars, aircraft, remote sensors, drones, medical devices, and robots. These need a database that requires no administrator, because there is nobody to administer it.

An application file format. Instead of inventing a proprietary binary layout or writing a pile of XML, desktop applications save their documents as SQLite databases. Version control systems, financial tools, CAD packages, and media catalogs do this. You get atomic saves, partial updates without rewriting the whole document, and the ability to query the file with tools you did not write. It is not necessary to use .sqlite as the extension for your application format.

Low to medium traffic websites. The sqlite.org guidance is that any site under 100,000 hits per day should be fine, and calls that a conservative estimate. For perspective, sqlite.org itself serves roughly 400,000 to 500,000 HTTP requests per day from SQLite. Most websites never come close to either number.

A cache in front of an enterprise database. Keep a local SQLite copy of the slices of data an application reads constantly. Reads stop crossing the network, the central server sheds load, and the application keeps working during an outage.

A data transfer format. A single compact file in a documented cross-platform format beats a directory of CSVs when you need to move structured data between systems and keep the types and relationships intact.

A file archive or container. The SQLite Archive format is a working substitute for ZIP or tar when you also want to query the contents.

A stand-in during demos and tests. A test suite can create a fresh database per test in memory, run against it, and throw it away, with no server to provision. <ChapterRef id="testing-with-sqlite" /> covers this.

## What SQLite is not good at

### One writer at a time

SQLite allows exactly one writer at any instant. Readers can run concurrently with each other, and in write-ahead logging mode readers can run concurrently with the single writer, but two writers never overlap.

For most applications this is a non-issue, because writes are short. Each one takes a few dozen milliseconds at most, and the next writer takes the lock as soon as the previous one releases it. Writers queue rather than fail, provided you have told the library to wait. Two settings make that work in practice, `PRAGMA journal_mode = WAL` and `PRAGMA busy_timeout` set to something like 5000 milliseconds, so that a blocked writer waits instead of returning an error immediately. <ChapterRef id="transactions-and-concurrency" /> covers both.

The setting has a ceiling. Somewhere above roughly 1,000 sustained writes per second, on ordinary hardware, the queue stops draining fast enough and a client/server engine becomes the better answer. That threshold moves with your disk, your transaction sizes, and how much work each write does, so treat it as an order of magnitude rather than a limit to design against.

### One file on one host

The database is a file on one machine. By default you cannot share it across machines, and putting it on network attached storage is a bad idea. SQLite relies on file locking to coordinate access, and network filesystem lock implementations are inconsistent enough that corruption is a real outcome rather than a theoretical one. The rule is to avoid any setup where several computers reach the same database file directly over a network, without an application server in between.

If you need the database in more than one place, you replicate it rather than share it. Litestream streams the write-ahead log to object storage for continuous backup, covered in <ChapterRef id="integrity-backup-and-restore" />. Turso puts read replicas on each machine, so reads are served locally while writes go to a remote primary, covered in <ChapterRef id="turso-and-libsql" />.

This is also what rules out most serverless platforms, and it is the way web applications most often get this wrong. A function on Lambda or Vercel gets a read-only deployment bundle and a scratch directory that disappears with the instance, and the platform runs as many instances as it likes, each with its own filesystem. A writable database there either vanishes or splits into as many divergent copies as there are instances, and moving it to shared network storage to fix that walks straight into the locking problem above.

Two arrangements do work. A read-only database shipped inside the bundle is an excellent fit, because there are no writes to coordinate. And Turso and Cloudflare D1 put a writable SQLite-compatible database behind a network protocol, which is the trade you make to get the engine's ergonomics on this kind of infrastructure. Note too that SQLite avoids the problem serverless usually has with client/server databases, where short-lived instances exhaust a connection pool. Opening a SQLite database is opening a file. <ChapterRef id="deployment" /> covers the hosting options.

### No fine-grained access control

There are no users, no roles, and no per-table or per-column grants. Access is all or nothing at the level of the file. Whatever authorization your application needs, your application implements. <ChapterRef id="security" /> covers the security consequences.

### Size

The documented maximum database size is 281 TB, raised from 140 TB in version 3.33.0. That number is a theoretical ceiling and not advice. In practice, once a single database approaches a terabyte, the operations around it get uncomfortable well before the format does, including backup windows, `VACUUM` time, and integrity checks. Treat a terabyte as the point where you start evaluating alternatives, and note that splitting one large database into several smaller ones is often the alternative you want. <ChapterRef id="multiple-databases" /> covers that.

## SQLite compared with Postgres and MySQL

The comparison is usually framed as a competition and it is not one. The SQLite developers put it plainly. Client/server engines exist to serve a shared repository of enterprise data, so they optimize for scalability, concurrency, centralization, and control. SQLite exists to provide local storage for a single application or device, so it optimizes for economy, efficiency, reliability, independence, and simplicity. The useful question is which problem you have.

Choose a client/server engine, such as Postgres or MySQL, when several separate programs need to reach the same data over a network, when the workload is write-heavy, when you need to run more than one application server against one dataset, when the data is heading toward a terabyte, or when you need database-enforced permissions per user.

Choose SQLite when one application owns the data. That covers desktop and mobile applications, command line tools, background jobs, test suites, caches, and a surprisingly large share of web applications, specifically the ones that run on a single server and will keep running on a single server.

The two also compose. Nothing stops you running Postgres as the system of record and SQLite as a local cache, an analysis workspace, or a transfer format, and plenty of production systems do exactly that.

One practical difference is worth naming early. Other SQL engines reject a string like `'banana'` in a column declared `INTEGER`. SQLite stores it. A declared type in SQLite is a preference for how values are converted, not a rule about what the column will accept, and the conversion is skipped when it cannot be done. <ChapterRef id="types" /> covers type affinity and the `STRICT` keyword, and explains why the default is what it is.

## Versions that matter

SQLite is one library, but which version of it you get is decided by your language runtime, your driver, or your operating system, and it is frequently not the newest. A .NET application gets its engine from SQLitePCLRaw rather than from the top-level package it references. A Python script gets whatever the interpreter was compiled against. A Node application may get one version from `node:sqlite` and a different one from `better-sqlite3`. Before you rely on a feature, check `select sqlite_version();` on the connection your application actually uses. <ChapterRef id="ecosystem-map" /> covers how to find out.

The features below are some of the ones whose absence changes how you write SQL. Appendix D has the full table.

Version 3.7.0, released 2010-07-21, added write-ahead logging. This is the setting that lets readers run while a writer works, and it is the first pragma most production configurations set.

Version 3.9.0, released 2015-10-14, added FTS5 for full text search, and the JSON functions.

Version 3.24.0, released 2018-06-04, added UPSERT in the PostgreSQL style, meaning `ON CONFLICT DO UPDATE` and `ON CONFLICT DO NOTHING`. Before this, the workaround was `INSERT OR REPLACE`, which deletes and reinserts the row and takes your other columns with it.

Version 3.25.0, released 2018-09-15, added window functions and `ALTER TABLE RENAME COLUMN`.

Version 3.31.0, released 2020-01-22, added generated columns, both virtual and stored.

Version 3.35.0, released 2021-03-12, added `RETURNING` on `INSERT`, `UPDATE`, and `DELETE`. This is the single most useful upgrade target for application code, because `RETURNING` removes a round trip after almost every write.

Version 3.37.0, released 2021-11-27, added `STRICT` tables.

Version 3.39.0, released 2022-06-25, added `RIGHT JOIN` and `FULL OUTER JOIN`. Older versions have `LEFT JOIN` only, and the standard workaround is to swap the tables or use a union.

Version 3.47.0, released 2024-10-21, shipped `sqlite3_rsync`, a utility that syncs one database to another by transferring only changed pages. <ChapterRef id="integrity-backup-and-restore" /> compares it with `.backup` and `VACUUM INTO`.

The most recent release at the time of writing is 3.53.4, from 2026-07-24.

## What the rest of this book assumes

From here on, the book assumes you are building an application that owns its database file, running on one host, with write-ahead logging turned on. That is the configuration where SQLite is at its best and it is the one most readers need.

Where a topic changes under a different setup, whether that is a read-only database shipped inside an application bundle, an in-memory database in a test suite, several attached databases, or replicas across machines, the chapter says so and points at the one that covers it.

## Takeaways

The points from this chapter that change what you do, rather than what you know.

- **Think "library, not server."** No process, no port, no
  connection, and a primary key lookup in microseconds. The same fact is
  why nothing outside the machine can reach the file. When SQLite behaves in a way
  that surprises you, this is usually the reason.

- **The fit question is ownership, not scale.** SQLite suits a database owned by one
  application on one host. The moment several programs on several machines need the
  same data, you want a client/server engine, however small the dataset is.

- **Set `PRAGMA journal_mode = WAL` and `PRAGMA busy_timeout` before anything else.**
  Journal mode is stored in the database file, so it is set once per database. The
  busy timeout is a property of a connection and defaults to zero, so set it on every
  connection your application opens, typically to 5000 milliseconds. Together they turn
  the single-writer rule into a queue. Without the timeout, a second writer gets
  `SQLITE_BUSY` immediately rather than waiting its turn.

  <ChapterRef id="transactions-and-concurrency" /> covers both.

- **Around 1,000 sustained writes per second is where you reconsider.** It is an order
  of magnitude, not a limit, and it moves with your disk and your transaction sizes.
  Reads have no equivalent ceiling.

- **Never put the database on a network filesystem.** Lock handling on NFS and SMB is
  inconsistent enough that corruption is a realistic outcome. If the data is needed in
  more than one place, replicate it with Litestream or Turso instead of sharing the
  file.

- **No writable database on serverless.** The filesystem is scratch space and there are
  as many of them as there are instances. A read-only database shipped in the bundle is
  an excellent fit; a writable one needs Turso or Cloudflare D1.

  <ChapterRef id="deployment" /> covers the options.

- **Your SQLite version is whatever your driver vendored.** It is compiled in, not
  installed, so you cannot upgrade it independently and two libraries in one process may
  differ. Run `select sqlite_version();` on the connection the application actually uses
  to check the version.

- **Access control is file permissions and nothing else.** Any rule finer than "this
  process may open this file" is your application's job.

  <ChapterRef id="security" /> covers the consequences.

- **A declared type is a preference, not a constraint.** An `INTEGER` column will accept
  `'banana'` and store it as text. Use `STRICT` tables when you want the rule.

  <ChapterRef id="types" /> explains why the default is what it is.

- **Copying the file is a backup only when nothing is writing.** A database in use has
  `-wal` and `-shm` beside it, and the `-wal` holds committed data the main file does not
  yet contain. For a copy taken while the database is live, use `.backup`, `VACUUM INTO`,
  or `sqlite3_rsync`. <ChapterRef id="integrity-backup-and-restore" /> compares them.
